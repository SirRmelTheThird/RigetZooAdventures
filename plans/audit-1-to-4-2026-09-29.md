# Codebase Audit 1-4

Date: 2026-09-29
Repository: `RigetZooAdventures`
Scope: Audit 1 Architecture and Design; Audit 2 Code Quality and Maintainability; Audit 3 Security and Reliability; Audit 4 Testing and Verification.

This is a read-only audit. No application source code, database schema, dependency, configuration, or test file was modified.

## Audit Summary

The application has a coherent PHP front controller, explicit request/response types, repository interfaces for several order/catalog paths, CSRF middleware, session regeneration on sign-in, Stripe signature verification, and a useful set of focused unit tests. The current checkout currency and webhook event-identity fixes are already represented by plans 001 and 002 in `plans/`, and the paid-order concurrency issue is represented by plan 003.

The highest-value work is to restore a trustworthy verification baseline and close the remaining payment/webhook reliability gap. The most important structural issue is inconsistency in the repository seam: order and catalog flows use injected interfaces, while authentication and rewards still call Eloquent models statically from services. The most important production security issue verified in this pass is that `public/index.php` enables `display_errors`; the most important webhook reliability issue is that replay state exists only in the request-local handler object.

### Verification baseline observed

- `composer test`: 110 tests and 212 assertions functionally pass, but exits 1 because PHPUnit reports 1 dependency deprecation and 7 notices.
- `composer lint`: exits 1 with widespread line-ending/end-of-file failures and additional formatting/line-length findings.
- `composer analyse`: exits 1 with PHPStan findings across production and test code, including an unused production method, missing iterable value types, and undefined Eloquent model properties/methods in tests.
- `composer validate --strict`: exits 1 because the empty PSR-4 namespace prefix is warned against.
- `composer audit --format=summary`: reports no security advisories.
- `php tests/autoload_check.php`: exits 1 because the CLI smoke script renders a view without `REQUEST_URI`, causing a warning and then a `TypeError` in `Navigation::pathOf()`.

The worktree was already dirty before this audit, with many modified and deleted application files. Findings describe the current checkout and do not attribute those unrelated edits to this audit.

## Audit 1 - Architecture and Design

### Scope

Inspected the front controller, route registration, router and middleware resolution, container wiring, repository contracts/adapters, service/model dependencies, checkout/order flow, and the repository's post-Audit design standards in `CODING_STANDARDS.md`.

### Findings

#### A1-001 Consolidate middleware execution behind the middleware pipeline

- **Priority**: High
- **Evidence**: `src/Core/Http/MiddlewarePipeline.php:10-29` defines `MiddlewarePipeline::default()` and `getOrdered()`, but a repository-wide search finds no caller. `routes.php:7-30` instead stores middleware as unqualified strings, while `src/Core/Http/Router.php:42-49` resolves and executes those strings directly.
- **Observed problem**: The codebase has two competing middleware designs: an unused ordered pipeline abstraction and route-local middleware arrays. The documented design standard explicitly requires the Auth-then-CSRF order to be enforced by a registered pipeline.
- **Impact**: Middleware ordering and registration can drift route by route; changing the pipeline class currently changes no production behavior. This weakens the intended authentication/CSRF invariant and makes cross-cutting middleware harder to test as one module.
- **Effort**: M
- **Risk**: MED; route behavior and middleware short-circuiting must remain unchanged.
- **Confidence**: HIGH
- **Fix sketch**: Make the router accept a middleware pipeline/resolver as its execution seam, register it in the container, and preserve explicit route membership while centralizing ordering and class-name resolution. Add router tests for authenticated POST routes and CSRF ordering.

#### A1-002 Route authentication and persistence through repository seams consistently

- **Priority**: High
- **Evidence**: `src/Services/Auth/AuthService.php:26-70` calls `Customer::where()`, `Customer::create()`, and `Customer::with()->find()` directly. `src/Services/Checkout/RewardService.php:27` calls `RewardPoint::create()` directly. By contrast, `src/Services/Tickets/BookingService.php:16-21` injects `OrderRepository`, and the documented standard requires service reads to go through injected repository interfaces.
- **Observed problem**: Service modules have inconsistent persistence seams. Authentication and rewards are coupled to Eloquent statics, while order/catalog modules use adapters.
- **Impact**: Auth and reward behavior cannot be tested with the same in-memory/fake adapter strategy as order behavior; database setup leaks into service tests and persistence changes require editing business services. This directly conflicts with the repository abstraction standard.
- **Effort**: M
- **Risk**: MED; query semantics, hashing mutators, uniqueness handling, and eager-loaded reward points must remain equivalent.
- **Confidence**: HIGH
- **Fix sketch**: Introduce focused interfaces for customer and reward persistence, provide Eloquent adapters and in-memory test doubles, bind them in `Container`, and move query/create details out of the services. Preserve the existing `Customer` password mutator or move hashing into an explicit domain/persistence policy with equivalent tests.

#### A1-003 Remove bootstrap side effects from container database resolution

- **Priority**: Medium
- **Evidence**: `src/Bootstrap/Container.php:196-213` catches any throwable from `Capsule::connection()`, conditionally requires `config/Bootstrap.php`, and retries the global connection. `public/index.php:8-9` already requires that bootstrap before constructing the container.
- **Observed problem**: The container silently repairs missing global database initialization by requiring a configuration file from inside a dependency factory. The same global initialization path is therefore both an application bootstrap responsibility and a hidden container fallback.
- **Impact**: Configuration errors can be obscured or retried after partial initialization; tests and alternate entry points inherit hidden global state. The container is harder to reason about and cannot be safely reused with an explicitly supplied connection or test double.
- **Effort**: S
- **Risk**: LOW; the public entry point already initializes the database before container use, but alternate callers may rely on the fallback.
- **Confidence**: HIGH
- **Fix sketch**: Make database initialization an explicit bootstrap/container dependency and remove the require-and-retry fallback. Add a container test that verifies missing initialization fails with a clear configuration exception and that the normal entry point still resolves services.

#### A1-004 Reduce container wiring concentration before adding more modules

- **Priority**: Medium
- **Evidence**: `src/Bootstrap/Container.php:84-145` builds a new factory map on every `make()` call, while the file is 507 lines and contains 37 methods/functions according to the audit inventory. The same class owns controller, repository, payment, notification, session, view, and database construction.
- **Observed problem**: The container is a large composition root with per-call factory-map allocation and many private factory methods. It is not an immediate correctness defect, but it is a high-churn coupling point.
- **Impact**: Every new module expands one class; constructor changes require editing a central file, and tests must resolve many unrelated infrastructure concerns to exercise a controller. The current shape also makes it easy for new dependencies to bypass the documented factory conventions.
- **Effort**: M
- **Risk**: MED; wiring regressions can break application startup.
- **Confidence**: HIGH
- **Fix sketch**: Keep one composition root but move declarative registrations into a stable factory map/property or small domain-specific provider registrations. Preserve singleton behavior through the existing `once()` mechanism and retain the universal container smoke test while splitting it by module family.

### Audit 1 conclusion

The repository has several genuine seams, especially around orders and payments, but they are not applied consistently. The first architectural change should be the middleware seam because it affects security ordering and is currently inert. Repository extraction for auth/rewards should follow characterization tests, not precede them.

## Audit 2 - Code Quality and Maintainability

### Scope

Inspected coding standards, static-analysis output, representative services/models/views, error/logging paths, configuration/bootstrap, dead-code signals, and the current test/quality scripts.

### Findings

#### A2-001 Establish a passing quality baseline before broad refactoring

- **Priority**: High
- **Evidence**: `composer.json:7-11` defines lint, format-check, PHPStan, and PHPUnit commands, but the current commands do not provide a green baseline. PHPCS reports widespread CRLF/end-of-file violations plus line-length and formatting errors; PHPStan reports production and test contract/type errors; PHPUnit exits nonzero on one deprecation and seven notices.
- **Observed problem**: The repository cannot distinguish a new regression from existing quality noise using its standard commands.
- **Impact**: Reviewers and future agents cannot rely on the stated verification gates. Formatting and type debt also obscure real defects, especially in Eloquent model access and array contracts.
- **Effort**: M
- **Risk**: LOW if handled as staged mechanical cleanup with no behavior changes; MED if formatting is mixed with refactoring.
- **Confidence**: HIGH
- **Fix sketch**: Record the baseline, fix standards and type errors in small scopes, configure legitimate framework/test exceptions explicitly, and make `composer test`, `composer lint`, and `composer analyse` meaningful gates. Keep dependency deprecation remediation separate from application behavior changes.

#### A2-002 Delete or complete dead code and stale abstractions

- **Priority**: Medium
- **Evidence**: `src/Services/Accommodations/AccommodationService.php:122-133` contains private `hasUnavailableDateOverlap()` marked deprecated/unused while `hasUnavailableDateOverlapFromRanges()` is the active implementation at lines 70 and 109. PHPStan also reports `src/Bootstrap/Container.php:479` method `sharedViewData()` as unused. `src/Core/Http/MiddlewarePipeline.php:10-29` has no production caller.
- **Observed problem**: Deprecated methods and unused composition abstractions remain alongside their replacements.
- **Impact**: Maintainers must determine which implementation is authoritative; stale code increases the chance that future fixes land in an inactive path or that old assumptions are accidentally revived.
- **Effort**: S
- **Risk**: LOW after repository-wide call-site verification; MED if compatibility callers exist outside the scanned tree.
- **Confidence**: HIGH for the two PHPStan-reported unused methods; HIGH for the unused pipeline caller search.
- **Fix sketch**: Confirm no external entry points depend on the methods, remove the dead method/unused factory, and either wire the middleware pipeline or remove it as part of A1-001. Add focused tests around the retained accommodation overlap behavior.

#### A2-003 Make view escaping an explicit invariant

- **Priority**: Medium
- **Evidence**: `src/Core/View/Format.php:10-19` provides the correct `htmlspecialchars` helper and most inspected views use it. `src/Views/layouts/layout-header-structure.php:6` emits `$documentTitle` directly, and `src/Core/View/ViewRenderer.php:45` exposes arbitrary extracted view data to PHP templates.
- **Observed problem**: Output escaping is convention-based rather than enforced by a shared view contract. The document title is a visible unescaped sink.
- **Impact**: A future dynamic page title or reused layout value can become HTML injection; the risk is currently limited because inspected page-title sources appear static, but the unsafe template pattern is easy to copy.
- **Effort**: S
- **Risk**: LOW; escaping a title changes only values containing markup.
- **Confidence**: MED for an exploitable current path, HIGH for the unsafe sink.
- **Fix sketch**: Escape the document title and document a strict “raw HTML only for named pre-rendered slots” rule. Add a renderer/template test that proves markup in a title is encoded while the intentionally pre-rendered actions slot remains unchanged.

#### A2-004 Replace weak type contracts around Eloquent data and arrays

- **Priority**: Medium
- **Evidence**: PHPStan reports undefined Eloquent properties/methods in `tests/Unit/Enums/OrderStatusTest.php` and `tests/Unit/Services/AccommodationServiceTest.php`, and missing iterable value types in support fixtures such as `tests/Support/FakeGateway.php` and `tests/Support/InMemorySessionStore.php`. `src/Services/Accommodations/AccommodationService.php:54-63` and `src/Repositories/Eloquent/Accommodation/EloquentAccommodationRepository.php:33-41` exchange untyped arrays for availability ranges.
- **Observed problem**: The type checker cannot reliably describe model attributes and array shapes at important business seams.
- **Impact**: Static analysis misses invalid attribute access and malformed availability data; test doubles can drift from production interfaces without a compiler signal.
- **Effort**: M
- **Risk**: MED; adding annotations may expose real behavior mismatches that require targeted corrections.
- **Confidence**: HIGH
- **Fix sketch**: Add model PHPDoc/property contracts or typed DTOs where appropriate, annotate array shapes and iterable value types, and make repository interfaces describe their collection/item types. Use the resulting PHPStan errors as a migration checklist rather than suppressing them globally.

### Audit 2 conclusion

The code is readable in the inspected modules and has useful naming, but maintainability is currently constrained by failing quality gates, stale code, and weak type contracts. The quality baseline should be repaired before a broad architectural extraction so failures remain attributable.

## Audit 3 - Security and Reliability

### Scope

Inspected the public entry point, routes, authentication and session handling, CSRF checks, request redirect handling, output paths, Stripe gateway/webhook handling, payment completion, transaction/idempotency code, notification transport, logging, migrations, and Composer advisories.

### Findings

#### A3-001 Disable error display in production entry points

- **Priority**: High
- **Evidence**: `public/index.php:5-6` calls `ini_set('display_errors', '1')` and `error_reporting(E_ALL)` unconditionally.
- **Observed problem**: PHP warnings, stack traces, file paths, and exception details can be written into HTTP responses in a deployed web entry point.
- **Impact**: Internal paths and implementation details can be exposed to unauthenticated users, and malformed requests can receive diagnostic output before the application error handler responds. This also conflicts with the application's own generic 500 response path in `src/Core/Error/ErrorHandler.php:82-107`.
- **Effort**: S
- **Risk**: LOW; local development needs a replacement environment-controlled setting.
- **Confidence**: HIGH
- **Fix sketch**: Make display errors environment-controlled and disabled by default for web requests; keep error reporting/logging enabled without sending diagnostics to clients. Add an entry-point/error-handler test or deployment check proving production configuration does not emit error details.

#### A3-002 Persist webhook event identity across requests

- **Priority**: High
- **Evidence**: `src/Services/Checkout/PaymentWebhookHandler.php:16` stores processed IDs in an instance array, and lines 43-50 use that array for replay suppression. `src/Bootstrap/Container.php:435-446` creates the handler through the per-request container, while `public/index.php:17-24` creates a new container for each HTTP request.
- **Observed problem**: The handler deduplicates repeated event IDs only within one PHP request. A retried Stripe delivery arriving in a later request is processed again and can resend the Discord notification.
- **Impact**: Webhook retries across requests are not idempotent; notification duplication and inconsistent operational records are possible during normal provider retry behavior or multi-worker deployment.
- **Effort**: M
- **Risk**: MED; durable claim/processing semantics must avoid dropping an event after a partial notification failure.
- **Confidence**: HIGH
- **Fix sketch**: Add a durable webhook-event repository/table keyed by verified event ID, with an atomic insert/claim operation and explicit processing outcome. Decide whether notification processing is at-least-once with idempotent downstream delivery or requires a retryable pending state. Extend the existing event-identity tests to cover separate handler instances/requests.

#### A3-003 Make paid-order completion concurrency-safe

- **Priority**: High
- **Evidence**: `src/Services/Tickets/BookingService.php:24-32` checks for an existing payment order before opening the transaction. `src/Repositories/Eloquent/Orders/EloquentOrderRepository.php:19-22` performs a normal lookup, and lines 34-38 calculate `max(order_number) + 1`. `database/migrations/CreateOrdersTable.php:14-17` provides unique payment and customer/order-number constraints.
- **Observed problem**: Concurrent completions can both observe no order; the database constraint protects the row but the losing request can surface a unique-key exception instead of returning the already-created order. The order-number calculation has a related race.
- **Impact**: A paid customer can see checkout failure on a retry, and duplicate side effects must be carefully prevented. This finding is already planned in `plans/003-concurrency-safe-paid-order-idempotency.md` and should not be duplicated as a new plan.
- **Effort**: M
- **Risk**: MED
- **Confidence**: HIGH
- **Fix sketch**: Execute the existing plan 003: keep uniqueness constraints, handle only the expected duplicate conflict or use an atomic repository operation, re-read the existing order, and prove inventory/reward effects occur once.

#### A3-004 Add response hardening headers at the response seam

- **Priority**: Medium
- **Evidence**: `src/Core/Http/Response.php:20-42` emits only Content-Type for HTML/JSON and Location for redirects. `public/index.php` serves browser-facing authenticated and payment pages.
- **Observed problem**: There is no centralized `X-Content-Type-Options`, `Referrer-Policy`, clickjacking protection, or CSP policy at the response seam.
- **Impact**: Browser defense-in-depth is weaker than necessary for pages containing authenticated sessions and payment UI. The exact CSP must account for the current external fonts, CDN styles/scripts, Stripe integration, and inline scripts.
- **Effort**: M
- **Risk**: MED; an overly strict CSP can break checkout or styling.
- **Confidence**: MED; the absence is confirmed, while exploitability depends on deployment and browser policy.
- **Fix sketch**: Add safe baseline headers centrally, then define and test a CSP from the actual external asset/payment requirements. Do not add a guessed policy without browser verification.

### Controls reviewed and not reported as defects

- Routes use server-side `AuthMiddleware` for profile and checkout and CSRF middleware for state-changing form routes (`routes.php:9-30`).
- Session cookies use `HttpOnly`, `SameSite=Lax`, strict mode, cookie-only mode, and regeneration on sign-in (`src/Core/Session/Session.php:12-44`, `src/Core/Session/Session.php:113-123`).
- Stripe webhook signatures are verified in `src/Payments/StripeGateway.php:74-91`.
- The inspected profile/order path scopes queries to the authenticated customer (`src/Services/Orders/OrderQueryService.php:16-21`, `src/Repositories/Eloquent/Orders/EloquentOrderQueryRepository.php:11-18`).
- Composer reports no known advisories.

### Audit 3 conclusion

The baseline auth and payment checks are stronger than a superficial scan suggests, but production error display and request-local webhook idempotency are concrete gaps. Existing plans 001 and 002 should remain the source of truth for currency and event-key correctness; plan 003 remains the source of truth for paid-order concurrency.

## Audit 4 - Testing and Verification

### Scope

Inspected PHPUnit configuration, Composer verification scripts, all test-file inventory, critical checkout/auth/cart/order/webhook tests, test doubles, integration test behavior, static-analysis output, and the CLI autoload smoke script.

### Findings

#### A4-001 Replace existence-only integration tests with behavioral integration tests

- **Priority**: High
- **Evidence**: `tests/Integration/BookingServiceTest.php:8-10` only asserts `class_exists(BookingService::class)`. `tests/Integration/PaymentWebhookTest.php:8-10` only asserts `class_exists(PaymentWebhookHandler::class)`. `tests/Integration/AuthServiceTest.php:14-20` constructs `AuthService` and asserts its instance is non-null without authenticating or registering a customer.
- **Observed problem**: Tests labelled integration do not cross a meaningful persistence, transaction, HTTP, or external-adapter seam.
- **Impact**: They can pass while booking, webhook, and auth behavior is broken. This is especially dangerous because the affected paths handle money, inventory, identity, and notifications.
- **Effort**: M
- **Risk**: MED; real database fixtures and deterministic test isolation are required.
- **Confidence**: HIGH
- **Fix sketch**: Replace each smoke assertion with observable behavior: booking persistence/rollback/idempotency, webhook verification and durable replay behavior, and auth registration/login/session behavior. Use transactions or isolated schemas and existing fakes where a full integration dependency is not required.

#### A4-002 Replace source/reflection assertions with public-behavior tests

- **Priority**: High
- **Evidence**: `tests/Unit/Services/BookingServiceTest.php:21-48` uses `ReflectionMethod` and `file_get_contents()` to assert private method names and the presence of the string `transaction`. It does not call `placePaidOrder()` with collaborators or assert order/side-effect behavior.
- **Observed problem**: The test suite asserts implementation shape rather than the module interface.
- **Impact**: Harmless refactors fail tests while real transaction, duplicate, reward, inventory, and rollback regressions can pass. This reduces test leverage and actively discourages architectural improvement.
- **Effort**: M
- **Risk**: LOW if characterization cases are added before deleting structural assertions.
- **Confidence**: HIGH
- **Fix sketch**: Build repository, writer, reward, logger, and transaction fakes at the public `OrderPlacer`/`BookingService` seam. Assert first completion, repeated completion, rollback propagation, and side effects; remove private-method/source-text assertions after behavioral coverage exists.

#### A4-003 Add critical failure-path and concurrency coverage

- **Priority**: High
- **Evidence**: `tests/Unit/Services/CheckoutServiceTest.php` covers several payment mismatch paths, but `tests/Integration/BookingServiceTest.php` has no booking behavior. `tests/Unit/Services/PaymentServiceTest.php:15-123` verifies same-instance event replay and distinct event IDs, but no separate-request durable replay. The existing payment/order plans explicitly identify currency, event identity, and concurrent paid-order completion as important paths.
- **Observed problem**: The most consequential behaviors are either unit-only or represented by placeholders; no test demonstrates transactional inventory/reward behavior under duplicate or failure conditions.
- **Impact**: Payment can succeed while order creation, inventory reservation, reward awarding, webhook retry, or rollback behavior regresses undetected.
- **Effort**: L
- **Risk**: HIGH; concurrency tests can be nondeterministic unless the repository seam or database transaction coordination is designed deliberately.
- **Confidence**: HIGH
- **Fix sketch**: Sequence work: characterize booking behavior, implement plan 003 with a deterministic duplicate test, then add integration coverage for transaction rollback and side-effect uniqueness. Add separate-handler webhook tests once durable replay storage is designed.

#### A4-004 Make the verification commands deterministic and green

- **Priority**: High
- **Evidence**: `phpunit.xml:4-18` enables `failOnWarning` and `failOnDeprecation`, but `composer test` currently exits 1 due to one dependency deprecation and seven notices. `composer.json:7-11` exposes lint and analysis gates that currently fail. `tests/autoload_check.php` fails on missing CLI request state.
- **Observed problem**: The repository advertises strict gates without a clean baseline or a documented distinction between application failures and environment/third-party notices.
- **Impact**: CI cannot serve as a trustworthy release signal, and planned refactors cannot use the required verification commands as acceptance criteria.
- **Effort**: M
- **Risk**: LOW to MED depending on whether the deprecation is fixed through a package upgrade or application input normalization.
- **Confidence**: HIGH
- **Fix sketch**: Fix or explicitly isolate the BigNumber float deprecation, remove PHPUnit notices, repair the CLI smoke fixture by supplying request globals or using a Request abstraction, then reduce PHPCS/PHPStan output in staged batches. Preserve `failOnWarning` and `failOnDeprecation` once green.

#### A4-005 Add security-boundary tests for sessions, CSRF, authorization, and output

- **Priority**: Medium
- **Evidence**: `tests/Unit/Core/RequestTest.php` and `tests/Unit/Core/ErrorHandlerTest.php` cover selected request/error behavior, but the inspected suite has no dedicated tests for `Session::start()` cookie configuration, session regeneration/invalidation, `CSRFMiddleware`, or the route-level combination of Auth then CSRF. `src/Core/View/Format.php:10-19` has the escaping helper, but the layout title sink at `src/Views/layouts/layout-header-structure.php:6` is not covered.
- **Observed problem**: Security controls are present but not protected by a focused regression suite.
- **Impact**: A future route or template change can remove CSRF/auth coverage or reintroduce output leakage without a failing test.
- **Effort**: M
- **Risk**: LOW; tests can use the existing in-memory session store and request objects.
- **Confidence**: MED; the repository-wide test inventory shows no obvious dedicated classes, but an external harness could exist outside the inspected tree.
- **Fix sketch**: Add focused tests for missing/valid CSRF tokens, unauthenticated protected routes, logout ordering, session fixation prevention, safe same-host redirects, encoded titles, and generic production error responses.

### Audit 4 conclusion

The suite has useful unit coverage for cart, validation, routing, checkout, and webhook event identity, but the critical integration layer is not yet meaningful. Behavioral tests and a green verification baseline must precede risky repository, middleware, and payment reliability changes.

## Prioritised Development Roadmap

The task IDs below preserve traceability to the findings above. Existing plans 001–003 are included rather than duplicated.

### Phase 1: Restore trustworthy verification and close exposed production behavior

#### T1.1 - Establish the verification baseline

- **Related findings**: A2-001, A4-004
- **Objective**: Make the standard Composer gates diagnostically useful and deterministic.
- **Known files**: `composer.json`, `phpunit.xml`, `tests/autoload_check.php`, affected files reported by PHPCS/PHPStan, and the test/support fixtures.
- **Dependencies**: None.
- **Approach**: Capture the current baseline; separate formatting-only changes from behavior; resolve PHPUnit notices/deprecation; fix the CLI request fixture; then address PHPStan contract errors and PHPCS failures in small batches.
- **Acceptance criteria**: `composer test`, `composer lint`, `composer analyse`, and `composer validate --strict` exit 0, or each intentional exception is explicitly configured and documented without hiding application errors. `php tests/autoload_check.php` exits 0.
- **Verification**: Run each command independently and inspect `git diff --check`; no formatter write mode during unrelated feature work.
- **Risk/prerequisite**: Do not combine this task with repository extraction or payment changes.

#### T1.2 - Disable production error display

- **Related findings**: A3-001, A4-005
- **Objective**: Prevent diagnostics from reaching web clients while retaining logging.
- **Known files**: `public/index.php`, `src/Core/Error/ErrorHandler.php`, environment/config documentation as needed.
- **Dependencies**: T1.1 is helpful but not required.
- **Acceptance criteria**: production/default web configuration has `display_errors=0`; generic HTML/JSON 500 responses contain no file path, trace, or exception message; local development can opt into diagnostics explicitly.
- **Verification**: add/run an entrypoint or error-handler test with a thrown exception and inspect response body/headers.
- **Risk**: LOW.

### Phase 2: Characterize critical behavior before changing seams

#### T2.1 - Replace placeholder integration tests

- **Related findings**: A4-001, A4-003
- **Objective**: Give auth, booking, and webhook paths real behavioral coverage.
- **Known files**: `tests/Integration/AuthServiceTest.php`, `tests/Integration/BookingServiceTest.php`, `tests/Integration/PaymentWebhookTest.php`, `tests/Integration/UniversalSmokeTest.php`, existing test bootstrap/support fixtures, and relevant services.
- **Dependencies**: T1.1.
- **Acceptance criteria**: no critical integration test is satisfied by only `class_exists`, `assertNotNull` on a newly constructed object, or equivalent wiring-only assertions; tests assert persisted or observable behavior and isolate their data.
- **Verification**: focused PHPUnit commands for each integration class, then `composer test`.
- **Risk**: MED; database availability and fixture isolation must be explicit.

#### T2.2 - Replace structural BookingService tests with behavior tests

- **Related findings**: A4-002, A4-003, A3-003
- **Objective**: Test the public booking interface and side-effect invariants.
- **Known files**: `tests/Unit/Services/BookingServiceTest.php`, `src/Services/Tickets/BookingService.php`, `src/Services/Orders/OrderWriter.php`, existing `FakePlacer`/repository doubles.
- **Dependencies**: T1.1; coordinate with existing plan 003.
- **Acceptance criteria**: tests cover first completion, sequential duplicate completion, transaction rollback, reward/inventory side effects, and unrelated persistence errors without inspecting private method names or source text.
- **Verification**: focused BookingService unit/integration commands and full suite.
- **Risk**: MED.

#### T2.3 - Execute existing payment correctness plans

- **Related findings**: Existing correctness audit plans 001, 002, 003; A3-003.
- **Objective**: Preserve already-planned currency validation, event identity, and paid-order concurrency fixes.
- **Known files**: The exact files and acceptance criteria are already specified in `plans/001-reject-payment-currency-mismatch.md`, `plans/002-deduplicate-webhooks-by-event-id.md`, and `plans/003-concurrency-safe-paid-order-idempotency.md`.
- **Dependencies**: T1.1 and T2.2 for plan 003's behavioral test seam.
- **Acceptance criteria**: follow each existing plan; do not create duplicate implementations or weaken database uniqueness constraints.
- **Verification**: each plan's focused PHPUnit/PHPStan commands plus full suite.
- **Risk**: MED to HIGH for concurrency handling.

### Phase 3: Restore architectural locality

#### T3.1 - Wire or remove the middleware pipeline

- **Related findings**: A1-001, A4-005
- **Objective**: Make Auth-then-CSRF ordering a real module invariant.
- **Known files**: `src/Core/Http/MiddlewarePipeline.php`, `src/Core/Http/Router.php`, `src/Core/Http/RouteResolutionStrategy.php`, `routes.php`, `src/Bootstrap/Container.php`, router/middleware tests.
- **Dependencies**: T1.1 and T2.1.
- **Acceptance criteria**: production dispatch uses one middleware execution seam; protected POST routes execute authentication before CSRF; existing route behavior remains unchanged; no unused duplicate pipeline remains.
- **Verification**: focused router/middleware tests and full suite.
- **Risk**: MED.

#### T3.2 - Introduce customer and reward repository seams

- **Related findings**: A1-002, A4-002
- **Objective**: Make auth/reward persistence replaceable and testable like order persistence.
- **Known files**: `src/Services/Auth/AuthService.php`, `src/Services/Checkout/RewardService.php`, new contracts/adapters under `src/Repositories`, `src/Bootstrap/Container.php`, auth/reward tests.
- **Dependencies**: T2.1 and T1.1.

- **Verification**: focused unit tests with doubles, integration tests with Eloquent, PHPStan, and full suite.
- **Risk**: MED.

#### T3.3 - Simplify container/bootstrap ownership

- **Related findings**: A1-003, A1-004, A2-002.
- **Objective**: Keep composition explicit and remove hidden initialization/dead registrations.
