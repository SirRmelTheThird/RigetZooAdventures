## Vetted findings

### [CORRECTNESS-01] Validate the payment currency before completing checkout

- **Evidence**: `src/Services/Checkout/CheckoutService.php:17` defines the application currency as `gbp`; `src/Services/Checkout/CheckoutService.php:43-55` checks payment success, customer ID, and amount but never compares `PaymentIntentState::$currency`.
- **Impact**: A succeeded payment in another currency with the same numeric minor-unit amount and matching customer metadata can be accepted as a GBP booking. The resulting order and cart total are recorded as though the payment were in the configured currency.
- **Effort**: S, including a focused unit regression test.
- **Risk**: LOW; the change adds a rejection branch before order placement and follows the existing mismatch/refund path.
- **Confidence**: HIGH; the currency value is present in the payment state but unused, while checkout hard-codes GBP.
- **Fix sketch**: Compare the retrieved intent currency with the configured checkout currency using a normalized representation. Route a mismatch through the existing refund-and-fail path and add a test proving no order is placed.

### [CORRECTNESS-02] Deduplicate Stripe webhooks by event identity, not payment intent

- **Evidence**: `src/Services/Checkout/PaymentWebhookHandler.php:40-48` uses `$event->intentId` as the replay key whenever it exists; `src/Payments/WebhookEvent.php:7-15` carries a distinct `$eventId`; `src/Payments/WebhookEventType.php:8-9` defines both succeeded and failed events for the same intent.
- **Impact**: Two legitimate Stripe events for one payment intent, such as a failure followed by a later success, share the same key. The first event suppresses the second, so the notification state can be permanently wrong. Replayed delivery of the same event should be ignored, but different event IDs must remain distinguishable.
- **Effort**: S, including a focused handler test with two event IDs sharing one intent ID.
- **Risk**: LOW; changing only the deduplication key preserves replay protection while allowing distinct lifecycle events.
- **Confidence**: HIGH; the code already transports event IDs and currently ignores event type when an intent ID exists.
- **Fix sketch**: Use the verified Stripe event ID as the replay key, with a deterministic fallback only for adapters that cannot provide one. Add tests for same-event replay and different-event-type events sharing an intent.

### [CORRECTNESS-03] Make paid-order idempotency safe under concurrent completion

- **Evidence**: `src/Services/Tickets/BookingService.php:24-32` checks `findByStripePaymentId()` before entering the transaction; `src/Repositories/Eloquent/Orders/EloquentOrderRepository.php:19-22` performs a normal lookup; `database/migrations/CreateOrdersTable.php:16` makes `stripe_payment_id` unique.
- **Impact**: Concurrent requests for the same successful payment can both observe no order and enter the transaction. One request may create the order while the other receives a uniqueness exception instead of returning the existing order, producing an avoidable checkout failure after payment. The same race pattern exists around the per-customer `max(order_number)+1` calculation at `EloquentOrderRepository.php:35-38` and the unique customer/order-number constraint in `CreateOrdersTable.php:17`.
- **Effort**: M, because the repository/transaction seam and concurrency regression test must be designed together.
- **Risk**: MED; changing duplicate handling must not swallow unrelated database errors or create duplicate inventory/reward side effects.
- **Confidence**: HIGH for the payment-intent race; the check is outside the transaction and the database uniqueness constraint is the only concurrent guard. The order-number race is a related secondary path requiring the same implementation review.
- **Fix sketch**: Move idempotency handling behind an atomic repository/transaction operation or explicitly handle only the expected unique-conflict case by re-reading the existing payment order. Preserve rollback semantics and prove concurrent or simulated duplicate completion returns one stable order ID.

## Findings considered and rejected

- **CLI autoload checker crash**: confirmed, but currently treated as verification/DX tooling failure rather than a production correctness defect because the web entry point supplies request globals. Revisit in a later DX/tooling audit.
- **Stale cart prices**: the cart stores quoted prices and checkout uses them, but the repository does not state whether quotes are intentionally locked. Needs product/price policy confirmation before classifying as a correctness defect.
- **Instance-local webhook replay storage**: the handler is request-scoped in the current container path and the webhook only sends notifications; durable replay storage may be a security/reliability concern, but it belongs in a later security/reliability audit unless production delivery semantics require durable state.
- **PHPCS, PHPStan, Composer warnings, PHPUnit notices/deprecation**: recorded as baseline quality/tooling failures and excluded from this correctness finding table.
